# 이미지 크기 조절기 이벤트 측정 개선

2026-11-06, 로컬 구현·검증 완료. 커밋·푸시·배포 및 GA4 계정 설정 변경은 하지 않았다. 이전 이미지 가이드 수정과 첨부 파일은 보존했다. 기존 진단은 [이벤트 측정 점검](./analytics-event-audit-2026-11-06.md)에 기록돼 있다.

## 적용 범위

| 파일 | 변경 |
| --- | --- |
| `src/lib/analytics.ts` | 기존 실행·다운로드 함수에 선택 인자 추가, 작업 결과 함수 추가. 다른 도구의 기존 호출은 같은 파라미터로 동작 |
| `src/app/tools/image/image-resizer/page.tsx` | 파일 추가·재적용별 파일 목록과 옵션을 고정하고 완료 결과를 한 번 집계. 중단된 작업의 결과 억제. 다운로드 방식·파일 수 추가 |
| `docs/analytics-event-audit-2026-11-06.md` | 후속 구현 보고서 링크 추가 |
| 이 문서 | 집계 정의, 검증 결과, 운영 반영 전 남은 확인 기록 |

도구 UI와 이미지 크기 계산, 출력 형식은 변경하지 않았다. 압축·변환·자르기 등 다른 도구에 신규 측정을 적용하지 않았다. 광고 코드·환경변수·GA4 계정 설정을 변경하지 않았고 라이브러리를 추가하지 않았다.

## 이벤트 계약

| 이벤트 | 기존 값·발행 시점 | 추가 값 |
| --- | --- | --- |
| `tool_execute` | 기존 `tool_name`, `tool_category`. 처리 시작 전 작업당 한 번 | `action_source=file_add 또는 apply`, `file_count` |
| `tool_result` (신규) | 해당 작업의 모든 파일 처리가 끝난 뒤 한 번 | `tool_name`, `tool_category`, `action_source`, `result=success 또는 partial 또는 error`, `file_count`, `success_count`, `failure_count` |
| `download_click` | 기존 `tool_name`, `file_type`. 개별은 저장 요청 직전, ZIP은 생성 성공 뒤 저장 요청 직전 | `download_type=individual 또는 zip`, `file_count` |

- 자동 처리의 `file_count`는 파일 읽기에 성공해 실제 리사이즈를 시작한 파일 수다. 읽기 실패·지원하지 않는 형식은 기존 실행 이벤트 발생 조건에 따라 제외한다. 모든 선택 파일의 유효성 검사 성공률을 측정하는 지표는 아니다.
- 재적용의 `file_count`는 기존대로 지원 MIME 형식인 파일 수다. 읽기 실패로 크기를 모르는 파일도 재적용 대상으로 포함되면 실패로 집계된다.
- 지원 파일이 0개인 재적용은 기존 실행 이벤트를 보존하고 `file_count=0`을 기록한다. 빈 작업의 성공 결과는 만들지 않는다. 이미지가 아예 없으면 기존 UI의 적용 버튼은 비활성 상태다.
- `success`는 대상 파일 전부 성공, `partial`은 일부 성공·일부 실패, `error`는 전부 실패다. 정상 완료 결과에서는 `success_count + failure_count = file_count`다.
- 여러 파일을 추가한 작업과 나중의 재적용은 서로 다른 작업이다. 파일 추가가 겹쳐도 각 작업이 시작할 때 정한 파일과 옵션을 기준으로 집계한다. React 렌더링이나 상태 updater 안에서 이벤트를 발행하지 않는다.
- 결과가 끝나기 전에 작업 대상 파일 하나라도 삭제하거나 전체 초기화·페이지 이탈이 발생하면 해당 작업의 결과 이벤트를 생략한다. 이미 기록된 실행 이벤트와 이미 완료된 다른 작업의 결과는 유지한다. 이미지 계산 자체를 강제로 중단시키는 신규 기능을 추가한 것은 아니다.
- 중단 사유를 별도 이벤트로 기록하지 않으므로 실행과 결과의 차이만으로 이탈·실패 원인을 확정할 수 없다. 결과가 없는 시도를 성공으로 간주하지 않는다.
- 개별 다운로드의 `file_count`는 1이다. ZIP은 실제 아카이브에 포함된 파일 수다. 기존 ZIP 구현은 같은 출력 이름을 덮어쓰므로 동일 이름 두 항목이 ZIP 파일 하나가 될 수 있다. 이 동작을 변경하지 않고 실제 포함 수를 기록한다.
- 다운로드 이벤트는 기기 저장 완료가 아닌 저장 요청을 뜻한다. ZIP 생성이 실패하면 기존과 같이 다운로드 이벤트를 기록하지 않는다.
- 기존 `tool_view`의 같은 문서 내 경로 중복 제거와 `guide_cta_click` 계약은 유지한다.

추가 분석 값은 고정 분류와 파일 개수뿐이다. 파일명·이미지 내용·원본 경로·오류 메시지·사용자 입력·작업 식별자를 전송하지 않는다. 내부 작업 구분용 파일 ID는 브라우저 메모리에서만 사용한다.

## 검증

최종 코드에서 `npm.cmd run lint` (경고·오류 없음), `npx.cmd --no-install tsc --noEmit`, `npm.cmd run build`와 후속 사이트맵 생성이 통과했다.

이고라이트에서 로컬 프로덕션 빌드의 실제 이미지 처리 → 브라우저 이벤트 대기열 → 다운로드 파일을 확인했다. Google 태그·Analytics·네이버 분석·광고의 외부 요청은 테스트 탭에서 차단했다. 아래는 운영 GA4 집계가 아닌 로컬 시나리오의 관측 결과다.

| 시나리오 | 결과 |
| --- | --- |
| 정상 PNG 두 개 한 번에 추가 | 실행 1회·결과 1회, file_add, 파일 2·성공 2·실패 0 |
| 같은 두 파일 160×200 재적용 | 별도 실행 1회·결과 1회, apply, 파일 2·성공 2 |
| 개별 PNG 및 ZIP 저장 | individual/1과 zip/2. 실제 PNG와 ZIP 속 PNG 두 개가 160×200 |
| 정상 두 파일 + 손상 PNG에 재적용 | partial, 파일 3·성공 2·실패 1 |
| 8000×8000 제한 초과 및 손상 파일 | error, 파일 3·성공 0·실패 3 |
| 지원하지 않는 파일만 추가 후 적용 | 기존 조건대로 추가 시 실행 없음. 적용 시 실행 1회·file_count=0, 결과 없음 |
| 두 파일 추가 작업이 겹친 뒤 각각 완료 | 각 작업당 결과 1회, 각 파일 수 1. 서로 섞이지 않음 |
| Canvas 완료를 지연한 뒤 파일 삭제·초기화·SPA 페이지 이탈 | 지연된 완료 후에도 해당 작업의 결과가 추가되지 않음 |
| 가이드에서 도구로 SPA 복귀 | 기존 tool_view 중복 제거 유지. 새 처리 작업은 정상 기록 |
| 390px 모바일 | 가로 넘침 없음, 첫 화면 파일 선택 가능, 실제 160×200 재적용 성공. 스크린샷 육안 확인 |
| 같은 이름 파일 두 개 ZIP 저장 | ZIP 실제 파일 1개, 이벤트 file_count=1 |
| 공유 함수 호환성 | 기존 gtag 호출의 파라미터 유지, dataLayer 대기열, 서버 측 호출 무동작 확인 |
| 로컬 HTTP·SEO | 가이드·리사이저·robots·두 사이트맵 HTTP 200. 페이지 canonical 유지·noindex 없음. 사이트맵 가이드 포함·URL 중복 없음 |

브라우저 자동화 초기에 로케이터 형식·대기 조건·아래쪽 링크 스크롤에서 실패했다. 현재 화면을 확인해 자동화 조건을 수정한 뒤 해당 시나리오를 완료했다. 페이지 이탈 테스트는 스크롤 제어가 실패해 화면에 확인된 링크의 DOM click을 사용했다. 제품의 링크나 UI 코드는 변경하지 않았다.

개인정보 없는 기존 샘플을 사용했다. 진단 스크립트·스크린샷·다운로드 파일은 Git 제외 경로 `output/playwright/resize-analytics-20261106/`에 저장했다. 별도 테스트 프레임워크를 추가하지 않았다. 확인한 브라우저 테스트 공간과 로컬 서버는 작업 종료 시 정리했다.

## 운영 반영 전 남은 확인

현재 변경은 로컬에만 있다. 이전 단계에서 운영의 기존 이벤트 수신은 확인했으나 **신규 tool_result와 추가 파라미터의 운영 GA4 수신은 검증하지 않았다.**

1. 승인된 배포 이후 실시간 보고서에서 신규 이벤트와 분류·파일 개수 값을 대조한다. 테스트와 자연 검색 성과를 구분한다.
2. 정규 보고서에서 분류를 사용하려면 `action_source`, `result`, `download_type`의 이벤트 범위 맞춤 측정기준, 파일 개수의 맞춤 측정항목 등록을 검토한다. 이번 작업에서는 등록하지 않았다. 기존 계정 확인 당시 이벤트 범위 측정기준은 7/50, 측정항목은 0/50이었다.
3. 기존 실행 수와 신규 성공 작업 수를 구분한다. 세션 유입 경로·방문 페이지와 연결한 실제 전환율은 아직 산출하지 않았다.

변환기의 옵션 변경 자동 처리와 전체 도구의 집계 통일, 취소 사유 이벤트, 같은 이름 ZIP 파일의 보존 방식 변경은 이번 범위에 포함하지 않았다.
