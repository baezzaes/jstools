# JSTools 이벤트 측정 점검과 최소 변경안

> 이 문서는 진단 단계의 기록이다. 이후 승인된 이미지 크기 조절기 최소 구현과 로컬 검증은 [후속 구현 보고서](./analytics-event-implementation-2026-11-06.md)에 정리했다.

## 범위와 상태

2026-11-06에 기존 GA4 전송 경로, 이미지 도구의 실행·다운로드 집계 기준을 확인했다. 이후 이고라이트로 GA4 실시간 수신까지 확인했다. 이전 단계의 이미지 가이드 미커밋 변경은 그대로 보존했다. 이번 단계에서는 제품 코드, GA4 계정 설정, 커밋·푸시·배포를 변경하지 않았다. 추가 파일은 이 보고서뿐이며 브라우저 진단 자료는 Git 제외 경로인 `output/playwright/`에 저장했다.

**완료한 범위:** 운영 브라우저에서 Google 수집 서버까지의 전송 확인, 로컬 집계 시나리오 검증, 소스 근거와 최소 변경안 정리, JSTools 웹 스트림 측정 ID 대조, GA4 실시간 이벤트 수신·다운로드 형식 값 확인, 맞춤 정의·할당량·데이터 필터 목록의 읽기 전용 확인.

**확인하지 못한 범위:** DebugView, 모든 이벤트의 전체 매개변수 값, 정규 보고서의 이번 테스트 반영, 데이터 보관·키 이벤트·세션 귀속 상세 설정. 수집 서버의 HTTP 204만으로 보고서 반영을 확정하지 않았으며 아래 별도 실시간 화면 확인으로 수신을 검증했다.

## 1. 실제 전송 확인

현재 루트의 Google 태그 측정 ID는 `G-F8GPFH41SR`이다. 운영 도메인에서 기존 가이드 상단 CTA를 한 번 클릭하고, 개인정보 없는 격자 PNG 파일을 추가해 크기를 적용한 뒤 개별 PNG 및 ZIP 다운로드를 각각 한 번 수행했다.

| 관측한 이벤트 | 이번 진단에서 관측한 수 | 전달된 기존 사용자 정의 파라미터 | Google 수집 응답 |
| --- | --- | --- | --- |
| guide_cta_click | 1 | guide_name, target_tool, target_url | 204 |
| tool_view | 1 | tool_name, tool_category, tool_url | 204 |
| tool_execute | 2 | tool_name, tool_category | 각각 204 |
| download_click | 2 | tool_name, file_type=png 또는 zip | 각각 204 |

이 수치는 서비스 운영 성과가 아니라 **한 번의 진단 흐름에서 관측한 이벤트 수**다. 기본 page_view 등은 위 표의 범위가 아니다. 모든 관측 요청의 측정 ID가 현재 소스와 일치했다.

사용자 정의 이벤트 파라미터에 파일명·이미지 내용이 없는 것을 확인했다. GA4의 기본 전송에는 페이지 주소·브라우저 식별 정보 등이 별도로 포함될 수 있다. 진단 결과에는 클라이언트 식별자나 원본 전체 요청을 기록하지 않았다.

진단 브라우저에서 임시 debug_mode 설정을 시도했지만 선별한 요청 필드에서 디버그 표시는 확인하지 못했다. 따라서 진단 이벤트가 일반 보고서에서 제외되었다고 보장하지 않는다. 운영 수치 비교 시 이 소량의 테스트 동작이 포함될 수 있음을 고려해야 한다. 사이트 소스에는 디버그 설정을 추가하지 않았다.

초기 Chrome 제어 오류로 GA4 화면을 읽지 못했으나, 사용자가 설치한 이고라이트의 로그인된 브라우저로 연결해 후속 확인을 완료했다. 로그인 정보나 세션을 추출하지 않았고 계정 설정도 바꾸지 않았다. 별도 GA4 연동 플러그인은 사용하지 않았다.

### 이고라이트 후속 실시간 확인

GA4 속성명 `JSTools`, 웹 스트림 이름 `JSTools`, URL `https://jstools-app.vercel.app/`, 측정 ID `G-F8GPFH41SR`을 화면에서 확인했다. 소스 및 이전 네트워크 관측 ID와 일치한다.

테스트 전 실시간 보고서의 최근 30분 활성 사용자는 0명이었다. 운영 가이드 → 상단 CTA → 도구 → 기존 격자 PNG 한 개 선택(자동 처리) → 비율 유지 해제 → 160×200px 크기 적용 → 개별 PNG 다운로드를 한 번 수행했다. 이후 실시간 보고서에 활성 사용자 1명과 다음 이벤트가 표시됐다.

| 이벤트 | 후속 실시간 보고서에 표시된 수 |
| --- | --- |
| guide_cta_click | 1 |
| tool_view | 1 |
| tool_execute | 2 |
| download_click | 1 |

이는 후속 테스트의 자동 처리·재적용과 개별 다운로드 동작에 부합하는 실시간 수신 증거다. 앞 표의 이전 네트워크 진단과 다른 테스트이며, 이고라이트에서는 ZIP을 다시 테스트하지 않았다. 이 수치를 검색 성과나 신규 방문자 증가로 해석하지 않는다. 일반 보고서에 테스트 트래픽이 포함될 수 있다.

`download_click`의 매개변수에서 `file_type=png`, 이벤트 수 1을 실제 화면에서 확인했다. 모든 이벤트의 전체 매개변수 값이나 DebugView까지 검증한 것은 아니다. 다운로드된 샘플 PNG의 실제 헤더 크기도 160×200px로 확인했다.

데이터 필터 목록에는 `Internal Traffic` 한 개가 표시됐으며, 유형은 내부 트래픽, 작업은 제외, 현재 상태는 **테스트**였다. 이 목록에 개발자 트래픽 필터는 표시되지 않았다. 내부 트래픽 판별 규칙이나 IP 목록은 열지 않았으며, 테스트 트래픽이 제외됐다고 주장하지 않는다.

맞춤 측정기준은 이벤트 범위로 `guide_name`, `tool_url`, `tool_name`, `tool_category`, `target_url`, `target_tool`, `file_type` 7개가 등록돼 있다. 할당량 화면은 이벤트 범위 측정기준 7/50, 사용자 범위 0/25, 상품 범위 0/10, 이벤트 범위 맞춤 측정항목 0/50을 표시했다. 제안한 `action_source`, `result`, `download_type` 등은 추가하지 않았다.

## 3. 로컬에서 검증한 시나리오

외부 분석 전송을 차단하고 현재 빌드에서 확인했다. 아래 숫자는 해당 테스트 문서 안에서의 누적 수다.

| 순서 | 실제 동작·결과 | tool_execute | download_click | tool_view |
| --- | --- | --- | --- | --- |
| 1 | PNG 두 개를 한 번에 추가, 두 개 모두 처리 완료 | 1 | 0 | 1 |
| 2 | 같은 두 파일에 160×200px 크기 적용, 둘 다 완료 | 2 | 0 | 1 |
| 3 | 개별 PNG 한 번 + 두 파일을 묶은 ZIP 한 번 다운로드 | 2 | 2 | 1 |
| 4 | 8000×8000px 적용, 두 파일 모두 최대 픽셀 제한 오류 | 3 | 2 | 1 |
| 5 | 가이드 링크로 이동 후 같은 문서에서 도구로 복귀 | 3 | 2 | 1 |

실패한 작업에서도 실행 횟수가 증가하고, 두 파일의 성공 처리가 한 번으로 기록되며, SPA 재방문이 조회 횟수를 증가시키지 않는 것을 확인했다. 이것은 현재 코드가 정의한 동작이며, 곧바로 전송 중복 오류라고 판단하지 않는다.

개별 PNG와 ZIP 파일 다운로드도 브라우저에서 확인했다. 브라우저 테스트가 파일을 관측한 사실과 제품 분석 이벤트가 저장 완료를 측정한다는 주장은 구분해야 한다.

## 4. 권장 집계 기준

검색 유입의 활성화를 평가할 때는 다음을 구분하는 것이 적절하다.

- **작업 시도:** 파일 추가 자동 처리 또는 사용자의 적용 요청 하나를 한 번의 작업으로 본다. 같은 작업의 파일이 여러 개여도 한 번이다.
- **작업 결과:** 작업에 포함된 파일이 모두 처리된 시점에 한 번 기록하며 성공·부분 성공·실패를 구분한다.
- **파일 수:** 작업 시도 수와 별도로 처리 대상·성공·실패 파일 수를 정수로 기록한다.
- **다운로드:** 현재 이벤트는 기존 발행 시점을 유지하고, 개별/ZIP과 포함 파일 수를 구분한다. 기기 저장 성공이라고 이름 붙이지 않는다.
- **유입 전환:** 세션 유입 경로와 방문 페이지로 나눈 세션 중 실행·성공 결과·다운로드 요청이 있는 세션의 비율을 본다. raw 이벤트 수를 활성 사용자 수로 나누지 않는다.

GA4 세션 귀속·필터와 맞춤 측정기준을 확인하기 전에는 실제 전환율 수치를 산출하지 않는다. 도구 간 횟수를 비교할 때도 발생 기준 차이와 변경 시점을 함께 기록한다.

## 5. 최소 변경안 — 아직 구현하지 않음

첫 적용 대상은 유입이 집중된 **이미지 크기 조절기**와 공유 분석 함수로 제한하는 것이 적절하다.

1. 기존 `tool_execute` 이름·기존 파라미터·발행 시점은 유지한다. `action_source=file_add|apply`와 `file_count`를 추가해 자동 처리와 재적용을 구분한다.
2. 새 `tool_result`를 작업 종료 시 한 번 기록한다. `result=success|partial|error`, `file_count`, `success_count`, `failure_count`, `action_source`, 기존 도구 식별 정보를 제안한다. 작업에 처리할 파일이 없는 경우를 포함해 0개·부분 오류·동시 작업의 정의를 구현 전에 확정한다.
3. 파일별 processItem이 명시적인 처리 결과를 반환하도록 최소 수정하고, 해당 작업이 시작될 때 정한 파일 목록의 결과를 기다려 작업 결과를 집계한다. 렌더링 상태를 useEffect로 감시해 결과 이벤트를 재발행하는 방식은 피한다. 재적용이 겹치거나 중간에 파일이 삭제되어도 서로 다른 작업을 섞지 않도록 확인한다.
4. 기존 `download_click`의 발행 시점은 옮기지 않는다. `download_type=individual|zip`, `file_count`를 추가한다. ZIP 준비 실패까지 알아야 할 경우 별도 오류 신호를 검토하되 초기 최소 범위에는 넣지 않는다.
5. 필요하면 실행·결과·다운로드에도 고정된 `tool_url`을 추가해 기존 tool_name과 함께 분석한다. 파일명·원본 경로·이미지 데이터·사용자 입력·원시 오류 메시지·지속 사용자 식별자를 추가하지 않는다.
6. 형식 변환기의 자동 재처리 누락과 tool_view의 SPA 재방문 기준은 별도 후속 범위로 분리한다. 이번 제안에서 전체 도구를 한꺼번에 바꾸지 않는다.

기존 이벤트를 성공 시점으로 단순히 옮기면 과거 실행 횟수와 의미가 달라진다. 따라서 기존 이벤트를 보존하고 결과 이벤트를 분리하는 안을 권한다. 새 차원은 action_source·result·download_type 같은 작은 고정값으로 제한하고, 파일 수는 측정항목으로 다루는 것이 적절하다. 계정에 등록된 맞춤 정의와 한도를 먼저 확인해야 한다.

## 6. GA4 계정에서 남은 확인

후속 확인 결과와 남은 범위를 구분한다.

1. **완료:** JSTools 웹 데이터 스트림이 `G-F8GPFH41SR`임을 대조했다.
2. **수신 확인 완료 / 일부 매개변수만 확인:** 실시간에서 guide_cta_click, tool_view, tool_execute, download_click을 확인했고 download_click의 file_type=png 값을 확인했다. tool_name·target_url 등 모든 값의 후속 화면 대조는 남아 있다. 이번 소량 진단과 다른 이용자 트래픽을 구분하며 합계가 항상 테스트 횟수와 같아야 한다고 가정하지 않는다.
3. DebugView는 해당 기기에 디버그 모드가 실제 적용된 것을 확인한 뒤 사용한다. 이 작업에서 DebugView 자체는 확인하지 못했다.
4. **목록 확인 완료:** Internal Traffic 필터의 테스트 상태, 기존 맞춤 측정기준 7개와 할당량을 읽기 전용으로 확인했다. 필터 규칙 상세는 확인하지 않았다. 필터를 바꾸거나 이벤트를 키 이벤트로 지정하지 않았다.
5. 유입별 전환 분석은 실시간의 제한적인 귀속 정보만으로 확정하지 말고 정규 보고서·탐색에서 세션 소스/매체·방문 페이지·도구를 연결해 확인한다.

GA4 실시간 수신은 확인했으므로 다음 구현 단계에서는 이미지 크기 조절기에 한해 자동 처리·재적용 구분과 작업 결과·개별/ZIP 구분을 추가하는 위 최소 변경안을 검토할 수 있다. 이번 단계에서는 신규 이벤트나 추가 기능 구현, GA4 맞춤 정의 추가를 시작하지 않았다.
