# 압축기 ZIP 파일명 충돌 수정 및 배포 전 검증

작업일: 2026-11-08 KST. 브랜치 `main`. 선행 보고서 `docs/image-guides-review-2026-11-08.md`를 읽고 진행했다. 기존 가이드 3개 파일의 미커밋 변경, 미추적 보고서·첨부자료를 보존했다. 이번에도 커밋·푸시·배포·GA4 설정 변경은 하지 않았다.

## 수정 범위와 방식

- 이번 추가 수정은 `src/app/tools/image/image-compressor/page.tsx`의 `downloadAll`과 압축 가이드의 ZIP 안내 문장뿐이다.
- 압축기는 기존에 같은 이름으로 `zip.file`을 호출해 앞의 파일을 덮어썼다. 변환기의 기존 접미사 방식을 읽었으나 변환기 코드는 수정하지 않았다.
- 압축기의 완료된 결과 전체에서 원래 출력 이름을 먼저 예약한다. 목록 순서대로 첫 이름은 유지하고, 중복이면 `-2`, `-3` 등의 숫자를 확장자 앞에 붙인다. 이미 사용한 이름뿐 아니라 다른 결과에 예약된 이름도 건너뛴다.
- 예를 들어 원래 이름 목록이 `sample-compressed.webp`, `sample-compressed.webp`, `sample-compressed-2.webp`라면 ZIP에는 순서대로 `sample-compressed.webp`, `sample-compressed-3.webp`, `sample-compressed-2.webp`가 들어간다. 뒤에 있는 원래 `-2` 이름을 먼저 가져다 쓰지 않는다.
- 이름 할당은 ZIP 생성 안에서만 이루어진다. `outputName` 상태, 압축 함수, 출력 형식, 품질, 개별 다운로드 이름·내용, ZIP 파일명, 이벤트 호출과 파라미터는 유지했다.
- 가이드의 ‘이름이 겹쳐 누락될 수 있다’는 임시 안내를 **‘ZIP 안에서 결과 파일 이름이 겹치면 숫자 접미사를 붙여 각 파일을 따로 저장합니다.’**로 바꿨다. 기존 본문 보강·메타데이터·URL·canonical은 보존했다.
- 라이브러리·공통 유틸리티·다른 도구 ZIP 처리·이벤트 확장은 추가하지 않았다.

## 실제 브라우저 ZIP 검증

개인정보 없는 640×480 PNG/JPG/WebP 샘플을 로컬 프로덕션 빌드에 추가했다. 파일 추가 후 실제 압축이 끝난 다음 ‘전체 ZIP 다운로드’로 파일을 받았다. JSZip으로 CRC를 검사하고, ZIP 엔트리를 브라우저에서 다시 디코딩했다.

| 시나리오 | 예상 파일 수 | 실제 파일 수 | 결과 |
| --- | ---: | ---: | --- |
| 같은 기본 이름 `sample.png`, `sample.jpg`, `sample.webp` | 3 | 3 | `sample-compressed.webp`, `sample-compressed.jpg`, `sample-compressed-2.webp` 모두 존재 |
| 같은 목록의 ZIP 재다운로드 | 3 | 3 | 이름·순서·파일별 SHA-256이 첫 다운로드와 동일 |
| 서로 다른 이름의 PNG·JPG·WebP | 3 | 3 | 세 파일 모두 기존 출력 이름 유지 |

동일 이름 시나리오의 원본→ZIP 대응:

| 원본 | ZIP 파일명 | 실제 형식 | 크기 | 바이트 |
| --- | --- | --- | --- | ---: |
| sample.png | sample-compressed.webp | image/webp | 640×480 | 1,504 |
| sample.jpg | sample-compressed.jpg | image/jpeg | 640×480 | 21,278 |
| sample.webp | sample-compressed-2.webp | image/webp | 640×480 | 7,264 |

각 ZIP 엔트리는 같은 위치의 화면 압축 결과 Blob과 바이트 단위로 일치했다. 개별 WebP 다운로드도 ZIP의 해당 파일과 바이트가 같았다. 위 숫자는 이 샘플에 한정된 관측이며 일반 압축 성능 수치가 아니다.

로컬 `dataLayer`에서는 세 ZIP 다운로드 요청과 한 개별 다운로드의 기존 `download_click` 계약(`tool_name`, `file_type`)만 확인했다. ZIP의 `file_type=zip`, 개별 파일의 `file_type=webp`가 유지됐다. 이는 GA4 실제 수신 확인이 아니다. 분석·광고 호스트를 테스트 탭에서 차단했고 GA4 계정에 접근하거나 설정을 바꾸지 않았다.

## 숫자 접미사 등 회귀 검증

기존 프로젝트에는 테스트 스크립트나 테스트 프레임워크가 없었다. 새 프레임워크를 설치하지 않고, 설치된 TypeScript·JSZip과 Node의 assert/vm을 사용한 진단 스크립트를 `output/playwright/compressor-zip-20261108/zip-regression.cjs`에 작성했다.

스크립트는 알고리즘을 별도로 복제하지 않는다. 현재 TSX에서 실제 `downloadAll` 함수를 찾아 TypeScript로 변환한 뒤, 준비한 완료 결과 목록을 주입해 실제 JSZip 아카이브를 생성한다. 숫자 접미사 이름은 UI의 현재 고정 출력 이름만으로는 직접 만들기 어려워 **생성 함수 단위로 명시적인 출력 이름을 주입한 검증**으로 구분했다. 실제 브라우저 UI에서 해당 이름을 입력했다고 주장하지 않는다.

| 함수 단위 시나리오 | 예상 파일 수 | 실제 파일 수 | 검증 |
| --- | ---: | ---: | --- |
| 같은 기본 이름 PNG/JPG/WebP 출력 | 3 | 3 | 접미사 부여, 원본 대응 유지 |
| 뒤에 기존 `-2` 출력 이름이 있는 경우 | 3 | 3 | 중복에 `-3` 부여, 기존 `-2` 보존 |
| 숫자 이름이 앞에 있고 숫자 이름 자체도 중복 | 5 | 5 | `-4`, `-2-2` 등으로 모두 보존 |
| 기존 `-2`, `-3`와 다중 중복 | 5 | 5 | `-4`, `-5`로 예약 이름 회피 |
| 서로 다른 이름 | 3 | 3 | 이름 유지 |
| 한글 이름과 숫자 이름 중복 | 4 | 4 | 한글·순서·파일 대응 유지 |
| 빈 완료 목록 | 0 | 0 | ZIP·다운로드 이벤트를 생성하지 않음 |

첫 더미 데이터 검사 후 실제 브라우저에서 만든 압축 이미지 바이트로 같은 검사를 다시 실행했다. 6개 비어 있지 않은 ZIP의 이미지 **23개**를 브라우저에서 모두 디코딩하여 JPG/WebP 파일 시그니처와 640×480 크기를 확인했다. 모든 아카이브의 엔트리 이름·개수·입력 순서·바이트 대응·CRC 검사가 통과했다. ZIP 생성 중 상태가 true→false로 복구되고 기존 ZIP 다운로드 이벤트가 1회 호출되는 것도 확인했다.

이 스크립트와 샘플·ZIP·JSON은 Git에서 제외되는 진단 자료다. 정식 테스트 체계를 새로 추가하지 않았다. 재실행 명령:

```powershell
node output/playwright/compressor-zip-20261108/zip-regression.cjs
```
